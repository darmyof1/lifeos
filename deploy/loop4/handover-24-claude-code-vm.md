## Part 1. Build (repo, in ~/work24)
a. `scripts/ops/backup-weekly.sh`: name archives `lifeos-backup-YYYYMMDD-HHMM.tar.gpg` (keep last 4 on the VM, keep working with the old date-only names); check that FILES.sha256 inside the archive is the manifest; update its tests.
b. `scripts/ops/backup-push.sh`: reads `~/loop1/backup.env` (BACKUP_REPO_URL, BACKUP_BRANCH; mode 600), keeps a clone in `~/loop1/backup-repo`, copies the newest archive and its .sha256 line into the clone, commits ("backup <name>", no other text), pushes; refuses if the archive is not gpg-encrypted data (check with `gpg --list-packets` or the file header), if the working copy is dirty, or if the push fails (no force push ever); dry run by default; `--execute` acts. A wrapper `scripts/ops/backup-run.sh` runs backup then push and writes one log line per run to `~/loop1/backups/run.log` (time, archive name, bytes, push result; nothing secret) and exits non-zero on any failure.
c. `scripts/ops/restore-backup.sh ARCHIVE_OR_REPO_DIR TARGET_DIR`: decrypts with the private key in the local keyring (asks for the passphrase itself; never takes one on the command line), extracts into TARGET_DIR (which must not exist or be empty and must not be under ~/loop1/workspaces or ~/loop1/state), verifies every file against FILES.sha256, prints the file count, the mismatch count and the elapsed seconds, exits non-zero unless there are 0 mismatches. It must work on macOS and Linux (no GNU-only commands: use `shasum -a 256` or `sha256sum`, whichever exists; no `stat -c`, no `date -d`). Also support `--latest` with a repo clone directory.
d. Tests (`tests/unit/test_backup_push.py`, `tests/unit/test_restore_backup.py`, update `test_backup_weekly.py`): throwaway key in a temp GNUPGHOME; a local bare git repository as the "remote"; cases: push works, no force push, refuses plaintext, refuses a dirty clone, restore matches, restore detects a changed byte, restore refuses a live folder, same-day second backup does not collide. Skip (not fail) when gpg is missing, like the existing backup test.
e. `deploy/loop1/health-check.py`: one new line "newest backup is younger than 8 days": reads the newest `~/loop1/backups/lifeos-backup-*.tar.gpg`; PASS if younger than 8 days; WARN if older; INFO if none yet. Put the logic in a function and test it like the other health-check functions (tests/unit/test_health_check_ledger_lines.py style).
f. `ops/recovery/backup-and-restore.md` (replace/extend backup-weekly.md): how it works, where each key lives, what is lost if the private key is lost (all backups unreadable), how to restore on a new machine from scratch (4 commands), and the Mac install note (`brew install gnupg` if gpg is missing). Update `ops/recovery/restore-drill.md` with a pointer. Straight quotes only; every APR number cited must exist (APR-0117 does).
g. Full unit suite and the validator in ~/work24 (all OK, 0 blocking).

## Part 3. Controlled drill (minutes, not a week)
D1. Back up the crontab (`crontab -l > ~/loop1/crontab.pre-loop4-$(date +%Y%m%d-%H%M)`).
D2. Dry runs of the three scripts from ~/work24, then ONE real run of `backup-run.sh --execute`. Check: archive on the VM; the backup repository has exactly one new commit containing only the .tar.gpg and the .sha256 line; a plaintext check on the repository content (search every blob for a few strings that exist in the agent files, such as the agent names in their AGENTS.md headings, expect 0 hits; do not print matches); sizes and timing.
D3. Cron test: add ONE temporary line `*/5 * * * * ... backup-run.sh --execute >> ~/loop1/backups/cron.log 2>&1 # lifeos-backup-drill` (absolute paths, same environment style as the other lines). Wait until it has fired twice BY CRON (about 10 to 12 minutes), then remove the line. Show the two run.log lines, two new commits in the backup repository, and that the crontab now equals the D1 backup (diff empty). If it does not fire or fails, show the cron.log, fix the cause (PATH, ssh, gpg) in the scripts only, and repeat; do not leave the temporary line in.
D4 (CEO, Mac terminal): the restore from another machine. Do this AFTER the CEO has pushed the patch (Part 4), because the restore script comes from the repo. Weekly line: after D4 passes, install `15 6 * * 0 ... backup-run.sh --execute >> ~/loop1/backups/cron.log 2>&1 # lifeos-backup-weekly` (Sunday 06:15 in the same time zone the 05:00 report line uses; check that it is outside 03:30 to 05:10). Show the crontab diff against D1: only that one line is new. Do not wait for it to fire.
D6. Health check: run it with the patched health-check.py (from ~/work24 for now): the backup line shows PASS; total PASS 75, WARN 0, FAIL 0.
